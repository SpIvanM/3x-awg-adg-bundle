Судя по твоим скриншотам, ты установил либо старую оригинальную ветку `x-ui` от vaxilu, либо какой-то урезанный форк, который не умеет генерировать конфиги для новых протоколов.

Панель — это просто графическая оболочка (кнопки и списки). Чтобы в выпадающем списке появился Hysteria2, тебе нужен самый продвинутый форк, который сейчас является стандартом для обхода ТСПУ —  **3x-ui от MHSanaei** .

Так как мы настраиваем сервер в США заново, проще всего накатить правильную панель поверх старой или с нуля.

### Шаг 1: Установка правильного форка (MHSanaei 3x-ui)

Подключись к своему серверу в США по SSH (через PuTTY, Termius или терминал) и выполни одну команду:

**Bash**

```
bash <(curl -Ls https://raw.githubusercontent.com/mhsanaei/3x-ui/master/install.sh)
```

**В процессе установки скрипт спросит тебя:**

1. Если обнаружит старую панель, спросит: `Do you want to customize the panel settings?` (Хотите настроить панель?) -> Нажми `y`.
2. Введи новый **Username** (логин для веб-морды).
3. Введи новый **Password** (пароль).
4. Введи **Port** (порт веб-панели, например `2053` или любой случайный. Не ставь 443, он нам нужен для трафика).

### Шаг 2: Обновление ядра (Критически важно!)

После установки зайди в веб-интерфейс новой панели (`http://твой_ip:порт`).

Даже если в списке протоколов появился Hysteria2,  **он не будет работать, пока ты не обновишь ядро** , так как протокол обрабатывает само ядро Xray, а не панель.

1. В левом меню перейди в раздел **Panel Setting** (Настройки панели).
2. Открой вкладку **Xray Version** (Версии Xray).
3. В выпадающем списке выбери **самую последнюю версию Xray-core** (на данный момент это будет версия `1.8.x` или новее).
4. Нажми кнопку **Update** (Обновить).
5. Подожди около минуты. Панель скачает новое ядро и перезапустится.

### Шаг 3: Настройка Hysteria2

Теперь, когда ты пойдешь в раздел **Inbounds** ->  **Add Inbound** , в выпадающем списке `Protocol` у тебя будет и `hysteria2`, и `vless`, и всё необходимое.

*Примечание:* Hysteria2 работает поверх протокола UDP. Убедись, что на твоем хостинге (Hostkey) в файрволе (если там есть внешний Firewall в личном кабинете)  **открыты UDP-порты** , которые ты укажешь в настройках Inbound'а. В самом Linux (Ubuntu/Debian) панель 3x-ui обычно прописывает правила iptables автоматически.

Ниже даю рабочий baseline, основанный на текущих официальных страницах 3x-ui и Xray/REALITY, а не на старых форумных рецептах.

**Что ставить**

- Для нового развёртывания я бы брал `3x-ui` только из актуального official release. На `2026-04-10` latest на GitHub был `v2.8.11`.
- Если хочешь меньше сюрпризов, ставь через `Docker Compose` по официальному примеру: `network_mode: host`, persistent volumes для `/etc/x-ui/` и `/root/cert/`, `XUI_ENABLE_FAIL2BAN=true`.
- Legacy-установку не используй.
- После первого входа сразу меняй `admin/admin`, включай 2FA и меняй panel web path.

**База сервера**

- Обнови ОС перед всем остальным.
- Поменяй SSH-порт и открой в firewall только то, что реально нужно.
- На старте оставь минимум открытых портов: SSH, HTTPS для панели, и порт(ы) инбаунда.
- DNS на сервере можно держать на `1.1.1.1` и `1.0.0.1`, если нет отдельной причины для другого.

**Панель**

- Панель лучше держать за HTTPS на отдельном домене.
- Если ставишь reverse proxy, используй Nginx или Caddy и проксируй panel backend на `127.0.0.1:2053`.
- Для подписок проксируй отдельный путь на `127.0.0.1:2096`, и следи, чтобы `URI Path` в панели совпадал с proxy path.
- Для Nginx важны WebSocket-headers и проброс client IP: `Upgrade`, `Connection`, `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Real-IP`, `Host`, `Range`, `If-Range`.
- Если панель доступна из интернета, ограничь её по IP или хотя бы спрячь за auth.

**Инбаунд**

- Для нового сетапа официальный текущий baseline такой: `VLESS + REALITY + xtls-rprx-vision + TCP/raw`.
- Делай один основной inbound/порт, а не россыпь транспортов.
- На сервере нужны:
  - UUID клиента
  - `flow = xtls-rprx-vision`
  - `privateKey` для REALITY
  - список `serverNames` без wildcard
  - `shortIds`
  - `target` на стабильный TLS 1.3 / H2 endpoint, как рекомендует README REALITY
- На клиенте должны совпасть:
  - UUID
  - `flow`
  - `serverName`
  - `shortId`
  - `public key`
  - `fingerprint = chrome` как нормальный дефолт
- Если делаешь схему сложнее, чем “один порт, один inbound”, сначала отлади базовую.

**Логи и лимиты**

- `fail2ban` держи включённым.
- Если нужен `limitIp`, access log должен быть включён.
- Если `limitIp` не нужен, access log можно отключить, особенно на слабом диске.
- Есть важный caveat: в текущем upstream issue `limitIp` может игнорироваться на `xtls-rprx-vision`, так что не считай это железной защитой без проверки на своей версии.
- Если используешь IP tunnel или CDN, IP-limit по умолчанию ломается, пока не передашь реальный IP клиента корректно.

**Что чаще всего ломает работу**

- Оставленный HTTP вместо HTTPS для панели.
- Несовпадение пути панели и reverse proxy.
- Не тот `flow` на клиенте.
- Забытая пара `serverName` / `publicKey` / `shortId`.
- Пытаются включить `limitIp` без access log.
- Пробуют тянуть всё через сложные tunnel/CDN-схемы до того, как заработал базовый вариант.
- Берут старый форумный гайд без проверки актуальности версии.

**Что я бы развернул на практике**

- `Debian 12` или `Ubuntu 22.04/24.04`
- `3x-ui` через `Docker Compose`
- домен для панели с HTTPS
- панель за reverse proxy
- `VLESS + REALITY + Vision + TCP` на одном порту
- `fail2ban` включён
- access log включён только если нужен `limitIp`
- регулярный бэкап `/etc/x-ui/` и сертификатов

На `512 MB RAM` я бы перевёл схему в максимально минимальный режим. Это уже не “комфортный” сервер, а узкий персональный узел, поэтому убираем всё лишнее.

**Что менять**

- `Не Docker` в базе. Для 512 MB я бы ставил `3x-ui` bare-metal через one-line install, потому что это рекомендованный путь в wiki, а Docker добавляет лишний слой и daemon overhead.
- `1 GB swap` как страховку. Это моя практическая рекомендация для такого малого RAM, чтобы не словить OOM на апдейтах и всплесках.
- `Один inbound`, без набора транспортов и экспериментов.
- `Без CDN`, без `IP tunnel`, без `WARP` на старте.
- `Без Telegram bot` и прочих доп. интеграций, пока не убедишься, что база стабильна.
- `Без IP limit`, если он не нужен. По wiki он требует `fail2ban` и `access.log`, а это лишняя нагрузка и место на диске.

**Рекомендованный профиль**

- `OS`: Debian 12 или Ubuntu minimal.
- `Install`: one-line script.
- `Panel`: HTTPS обязательно, но на 512 MB я бы по возможности избегал отдельного reverse proxy и использовал встроенный SSL/ACME в 3x-ui.
- `Security`: смена `admin/admin`, `2FA`, random web path, firewall, смена SSH-порта.
- `Xray`: `VLESS + REALITY + xtls-rprx-vision + TCP`.
- `Logs`: `XUI_DEBUG=false`, `XUI_LOG_LEVEL=warn`.
- `Fail2ban`: `true`, если панель открыта в интернет; если панель строго закрыта firewall/IP allowlist, можно выключить, чтобы сэкономить немного ресурсов.
- `Access log`: `none`, если IP limit не нужен. Если IP limit нужен, включай `access.log` и принимай дополнительную нагрузку.

**Что я бы не делал на 512 MB**

- Не ставил бы `Docker Compose` как основной вариант.
- Не поднимал бы reverse proxy без необходимости.
- Не включал бы сразу все функции панели.
- Не рассчитывал бы на много одновременных клиентов.

**Если нужен reverse proxy**

- Тогда только `Nginx`, с правильными заголовками `X-Forwarded-For`, `X-Real-IP`, `X-Forwarded-Proto`, и путь панели должен заканчиваться на `/`.
- Для `/sub` путь должен совпадать с настройкой `URI Path`.
- Но это уже не оптимальный путь для 512 MB, а запасной вариант.

**Практический вывод**

- На `512 MB` делай “минимальный боевой набор”: `bare install + swap + один inbound + HTTPS + минимум логов`.
- Если это публичный или многопользовательский сервер, `1 GB RAM` уже заметно спокойнее.
