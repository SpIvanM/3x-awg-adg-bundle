# Поэтапный план: разделение `10-helpers.sh` и последовательная миграция к Target + Relay

## 1. Role
You are a Senior Shell and Network Engineer with expertise in modular Bash installers, Linux networking, UFW/iptables, AmneziaWG, AdGuardHome, and operator-guided interactive setup flows.

## 2. Essence
Нужно не просто доделать архитектуру `target|relay`, а сначала сделать кодовую базу удобной для последовательной работы. Для этого монолитный [`src/setup/10-helpers.sh`](/C:/Users/ivanm/Documents/Projects/3x-awg-adg-bundle/src/setup/10-helpers.sh) надо разбить на отдельные helper-модули `AWG / AGH / 3x / port forwarding`, а затем выполнять архитектурные изменения строго по этапам. Каждый этап должен быть независимым, давать отдельное улучшение, начинаться с падающих тестов и заканчиваться зелёными тестами, обновлёнными описаниями файлов, сборкой `setup.sh`, отдельным commit и только после последнего этапа merge.

## 3. Task

1. Этап 1. Baseline сценариев `--mode` `[считать выполненным]`

Требования: `DEPLOY_MODE="target"`, парсинг `--mode`, лог режима, обновлённый usage и версия остаются опорной точкой для следующих этапов.  
Результат: дальнейшие задачи не затрагивают уже выполненный фундамент без необходимости.

2. Этап 2. Разделение `10-helpers.sh` на специализированные helper-модули  
TDD: сначала добавить падающие проверки в `script-regressions.ps1` на новый список source-модулей, новый порядок сборки, отсутствие `10-helpers.sh` в build list и наличие новых файлов в `src/setup/README.md`; затем прогнать тесты и увидеть падение.  
Требования: заменить `10-helpers.sh` на `10-common.sh`, `11-awg-helpers.sh`, `12-agh-helpers.sh`, `13-3x-helpers.sh`, `14-port-forwarding-helpers.sh`.  
Требования: в `10-common.sh` оставить только общие функции чтения credentials, CRLF-normalization и общие утилиты.  
Требования: в `11-awg-helpers.sh` перенести AWG-функции.  
Требования: в `12-agh-helpers.sh` перенести AGH-функции.  
Требования: в `13-3x-helpers.sh` перенести legacy `x-ui/3x` cleanup и все будущие helper-функции для интерактивной установки `3x-ui`.  
Требования: в `14-port-forwarding-helpers.sh` выделить весь будущий relay-forwarding слой.

Требования: на этом этапе не менять целевое runtime-поведение, кроме внутренней структуры модулей.  
Результат: кодовая база становится пригодной для безопасной пошаговой доработки без монолитного `10-helpers.sh`.

3. Этап 3. Удаление legacy `Xray/cascade` и ввод ручного installer-flow для `3x-ui`  
TDD: сначала добавить падающие проверки на отсутствие `install_xray_core`, `write_xray_config`, `CASCADE_*`, `ADG_HTTP_PROXY_PORT`, `VLESS_LINK`; добавить проверки на наличие `13-3x-helpers.sh`-функции интерактивного запуска `3x-ui`; затем прогнать тесты и увидеть падение.  
Требования: полностью удалить из source-модулей старую Xray/cascade-архитектуру.  
Требования: добавить helper, который запускает официальный installer `3x-ui` в интерактивном режиме через `/dev/tty`.  
Требования: скрипт не должен выполнять silent install и не должен конфигурировать `3x-ui` автоматически.  
Требования: после установки скрипт только сообщает оператору, что дальнейшая настройка `3x-ui` выполняется вручную вне скрипта.  
Требования: если `--mode relay` ещё не готов на следующих этапах, он должен завершаться понятным fail-fast сообщением, а не полурабочим состоянием.  
Результат: проект избавляется от legacy логики и получает новый допустимый способ работы с `3x-ui`, соответствующий вашему ограничению.

4. Этап 4. Завершение сценария `target` как первого сервера топологии  
TDD: сначала добавить падающие проверки на `AWG_PORT=53`, `MTU = 1280`, отсутствие AGH HTTP proxy, target-specific output с `IP / AWG 53 / Reality 443 / DNS port`, а также на target-specific firewall markers; затем прогнать тесты и увидеть падение.  
Требования: в `target` локальный AWG работает на `53/udp`.  
Требования: добавить `MTU = 1280` в серверный и клиентский AWG-конфиг.  
Требования: расширить и сохранить обфускационные параметры AWG идемпотентно.  
Требования: AGH работает только direct, без зависимости от Xray/HTTP proxy.  
Требования: output для `target` должен явно отдавать данные, которые нужны для настройки `relay`: IP, `AWG 53`, `Reality 443`, DNS endpoint.  
Требования: шаг установки `3x-ui` в `target` только запускает installer и печатает ручной handoff, без автонастройки панели.  
Результат: `--mode target` становится самодостаточным первым этапом развёртывания и выдаёт всё, что нужно второму серверу.

5. Этап 5. Завершение сценария `relay` как локального direct-стека без forwarding  
TDD: сначала добавить падающие проверки на `prompt_target_details()` через `/dev/tty`, сохранение `TARGET_IP`, `TARGET_AWG_PORT`, `TARGET_REALITY_PORT`, `TARGET_DNS_PORT`, relay-local `AWG_PORT=53` и relay-specific output; затем прогнать тесты и увидеть падение.  
Требования: `relay` должен запрашивать параметры `target` интерактивно.  
Требования: `relay` поднимает собственные локальные AWG, AGH и шаг интерактивной установки `3x-ui`.  
Требования: локальный AWG на `relay` тоже работает на `53/udp`, потому что это отражено в источнике истины `AGENTS.md`.  
Требования: на этом этапе forwarding ещё не включается, но все данные для него уже собираются и сохраняются.  
Требования: output должен явно разделять локальный direct-стек relay и будущие внешние relay-forward endpoints.  
Результат: `--mode relay` уже полезен как самостоятельный локальный стек и готов к последнему сетевому этапу.

6. Этап 6. Transparent Port Forwarding для `relay`  
TDD: сначала добавить падающие проверки на наличие `setup_port_forwarding()`, `cleanup_port_forwarding()`, `RELAY_FWD_AWG_PORT`, `RELAY_FWD_REALITY_PORT`, persistence через `iptables-save` или `netfilter-persistent`, а также на отсутствие ложной проверки NAT через `ss`; затем прогнать тесты и увидеть падение.  
Требования: реализовать выбор внешних relay-forward портов с проверкой занятости.  
Требования: настроить `PREROUTING`, `FORWARD`, `POSTROUTING` для прозрачного relay-forwarding `UDP -> Target:53` и `TCP -> Target:443`.  
Требования: правила должны быть идемпотентными и сохраняться после перезапуска.  
Требования: cleanup должен удалять только свои правила, без глобального flush.  
Требования: UFW должен открывать отдельно локальные relay-порты и отдельно forwarding-порты.  
Результат: `relay` начинает соответствовать сетевой части топологии из `AGENTS.md`.

Требования: обновить `uninstall.sh` под новые helper-модули, manual `3x-ui` flow и точечный cleanup forwarding-правил.  
Требования: обновить `src/setup/README.md`, `readme.md` и описания изменённых файлов на русском.  
Требования: обновить общий индекс модулей и generated header сборки.  
Требования: после завершения этапа выполнить полную сборку `setup.sh`, прогнать весь `script-regressions.ps1`, получить `exit code 0`, затем сделать финальный commit sequence и merge.  
Результат: код, сборка, документация и uninstall синхронизированы и готовы к нормальной дальнейшей разработке.

## 5. Format
- Каждый этап исполняется строго отдельно и последовательно.
- Для каждого этапа цикл одинаковый: добавить тесты этого этапа → запустить тесты и увидеть падение → реализовать только этот этап → пересобрать `setup.sh` → снова запустить тесты и получить зелёный результат.
- После каждого этапа обязательно обновлять описания затронутых файлов и общий индекс source-модулей.
- После каждого этапа делать отдельный атомарный commit.
- После последнего этапа делать merge итоговой версии.

## 6. Limitations
- Не объединять два этапа в один commit.
- Не добавлять заранее тесты следующих этапов.
- Не сохранять monolithic `10-helpers.sh` как рабочий source-модуль после этапа 2.
- Не делать silent install или auto-config `3x-ui`.
- Не возвращать legacy `CASCADE_*`, `XRAY_*`, `VLESS_LINK`, `ADG_HTTP_PROXY_PORT`.
- Не использовать destructive cleanup вроде `iptables -t nat -F`.

## Assumptions
- Именование новых helper-модулей принимается в виде `10-common.sh`, `11-awg-helpers.sh`, `12-agh-helpers.sh`, `13-3x-helpers.sh`, `14-port-forwarding-helpers.sh`.
- Этап 1 уже завершён и не пересобирается заново, если только следующий этап не выявит прямой дефект в baseline.
- Ручная конфигурация `3x-ui` остаётся внешним операторским шагом и не включается в scope автоматизации.
